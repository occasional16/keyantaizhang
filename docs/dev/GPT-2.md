> **这个项目当前已经是一个“可用的内部自动化原型”，但还不是一个可直接商业化出售的产品。**

不过，因为 `.gitignore` 明确排除了 `.xlsx/.xlsm` 和真实 `raw_data`，我目前能做的是**源码级审查**，不能实际拿你的 `console_dashboard.xlsm + teachers_profile.xlsx + WOS/EI/CNKI` 跑一次端到端测试。

## 一、先纠正上一轮：你的项目不是“科研项目台账”

真正的 pipeline 是：

**WOS / EI / CNKI**

↓

按正式出版年份筛选

↓

根据课题组成员姓名/拼音认领论文

↓

DOI + 标题跨库去重

↓

合并 SCI/EI 等收录标签

↓

只保留课题组成果

↓

输出统一的 7 列 Excel 成果表。

README 对此写得很明确。

而且 `Mod2_CleanRawData.bas` 确实实现了这条链路，不是文档里的“未来规划”。

这意味着你的真正竞品不是 Notion、Excel 项目管理，也不是经费管理 SaaS。

而是：

**科研秘书手工 Excel + 高校科研管理系统 + 各种科研成果库/团队科研管理平台。**

目前市场上已经存在相当直接的重叠产品。例如“科研星”明确提供课题组成果库、成果智能导入、按年份/作者/分区导出等功能；数塔也已经把“成员成果自动汇聚、PI 总览、按项目/成员/时间统计”作为课题组功能。

所以你不是在一个无人区里。

但这并不意味着没机会。

## 二、代码里我认为真正有产品价值的部分

### 1. “多源 → 单一成果账本”这个闭环是成立的

你不是单纯做：

> WOS 导出转 Excel。

而是在尝试解决：

> WOS 有一份  
> EI 有一份  
> CNKI 有一份  
> 同一篇论文重复  
> 作者名字格式不同  
> 有些不是本组成果  
> 年份还可能跨期  
> 最后行政人员需要一张统一表。

这一点很重要。

`Mod2` 已经针对 WOS、EI、CNKI 分别做字段适配，再汇入统一记录。

这是一个**具体且真实的 workflow**，而不是 CRUD。

---

### 2. DOI + 标题双键去重，是对的产品思路

代码先用 DOI，找不到再用归一化标题：

```text
DOI
↓
Normalized title
↓
record ID
```

并在重复时合并 `SCI+EI`，同时补齐缺失卷期。

这个逻辑虽然还需要改进，但方向是对的。

因为真正给科研秘书节省时间的不是：

> “把 Excel 做漂亮一点。”

而是：

> **“原来我要人工比 700 条记录，现在你替我判断。”**

商业价值主要产生在这里。

---

### 3. “只认领本组成员”也是核心价值，而不是边角功能

你专门做了一个 `teachers_profile` → 拼音/缩写/变体 → 作者匹配体系。`Mod1` 会生成诸如：

- `Lu, Xinchun`
- `Lu, Xin-chun`
- `Lu, XC`
- `Lu, X.C.`
- `Xinchun Lu`

等大量候选格式。

然后 `Mod2` 再把数据库里的作者与这些别名比对，只输出本组作者。

这一点比单纯的数据转换器有价值得多。

## 三、但是我发现了几个相当严重的问题

这里开始是我认为你目前最需要听的部分。

### 第一严重问题：控制台存在“算出来的假统计”

这是我读代码时最警惕的一段。

在 `刷新控制面板数据()` 里，所谓“非本室/排除条目”**不是根据当前实际 pipeline 统计得到的**。

而是：

```vb
If finalMergeCount = 545 Or finalMergeCount = 711 Or finalMergeCount = 0 Then
    excTotal = 166
    ...
ElseIf finalMergeCount = 186 Then
    excTotal = 57
...
Else
    excTotal = Round(finalMergeCount * 166 / 545)
```

也就是说，如果没有命中几个预设数量，就根据历史比例**推算一个排除数量**。

这个在个人原型阶段可以理解为临时占位，但：

> **产品化以前必须彻底删除。**

因为你的产品卖点恰恰是：

> 科研成果统计准确。

如果 dashboard 中出现“看起来很精确、实际上是比例估出来”的数字，对科研行政类产品是致命的。

更麻烦的是，`Mod2` 本来已经真实维护了：

- `excludedCount`
- `outOfDateCount`

所以完全可以把真实统计结果写入状态表，而不是估计。

这是我建议你**第一优先级修复**的东西。

## 四、第二个问题：README 的“智能消歧”说得比代码实际能力强很多

README 写的是：

> “深度模糊匹配”“智能消歧”。

但真正代码的本质其实是：

> **预生成大量 alias → 规范化 → 精确字典匹配。**

`ExtractLabAuthors()` 最后做的是：

```vb
If dictTeachers.Exists(authNorm) Then ...
ElseIf dictTeachers.Exists(...) Then ...
```

不是统计意义或实体消歧意义上的 fuzzy matching。

这在小课题组里可能非常好用。

但产品化会遇到一个严重问题：

#### 王军 vs 王静

如果两个人最后都有：

> Wang, J.

你的 dictionary 当前是：

```vb
d(alias) = cName
```

后写进去的人会覆盖前一个。

于是：

> `Wang, J` → 某一个人

而不是：

> `Wang, J` → [王军，王静] → 待消歧。

更危险的是，你还主动生成了**单首字母缩写**作为候选。

因此团队越大，误认概率越高。

## 五、真正的产品级作者消歧应该怎么做？

我建议以后不要：

> alias → person

而是：

> alias → candidate persons[]

然后计算 confidence：

**姓名全拼完全命中**

+3

**所在机构一致**

+3

**常见合作者一致**

+2

**ORCID 一致**

+10

**邮箱一致**

+10

**研究领域合理**

+1

然后：

> 0.98 → 自动认领  
> 0.72 → “请确认是不是张三”  
> 0.40 → 不认领

这时你才能真正把：

> “智能消歧”

作为产品卖点。

而且这个方向以后确实有可能成为你的**核心技术资产之一**。

## 六、第三个问题：拼音系统目前不适合作为产品底座

你现在的 `GetCharPinyin()` 是一个巨大的：

```vb
Select Case ch
Case "丁": ...
Case "七": ...
...
```

手工汉字→拼音映射库。

而且最后：

```vb
Case Else
    GetCharPinyin = ""
```

也就是说，遇到字典没有覆盖的字，直接返回空字符串。

对于内部项目，这是典型的：

> **能把自己课题组跑通就够了。**

对于商业产品则不行。

用户第一次导入一个名字，比如某个生僻字，你的系统把这个成员漏掉，他不会理解“拼音字典覆盖率问题”，只会得出结论：

> “这个软件不准。”

所以产品化以后应该：

**不要自己维护汉字拼音表。**

更进一步，我甚至建议：

> 中文姓名 → 自动拼音

只作为“候选建议”。

真正 author identity 应该允许用户保存：

- 中文名
- preferred English name
- WOS author name
- Scopus ID
- ORCID
- ResearcherID
- 自定义 alias

这样更稳。

## 七、第四个问题：CNKI = 中文核心，目前逻辑上不成立

你的 CNKI importer 里只要是 CNKI 数据：

```vb
AddOrMergeRecord(..., "中文核心", ...)
```

也就是说：

> **进入 CNKI 文件 = 中文核心论文。**



除非你强制要求用户：

> “CNKI 文件只能事先筛选为中文核心期刊。”

否则这是明显的分类错误。

CNKI ≠ 中文核心。

这里产品化以后应该变成：

> CNKI = 中文论文来源

然后根据：

- 北大核心目录
- CSSCI
- CSCD
- 科技核心
- 用户单位自己的认定目录

再打标签。

而这件事情反倒很有商业价值。

因为高校/单位真正需要的经常不是：

> “有多少 CNKI 论文？”

而是：

> SCI 一区多少？  
> 中科院一区多少？  
> Top 多少？  
> CSSCI 多少？  
> 北大核心多少？  
> 本单位 A/B/C 类多少？

**“评价规则映射”可能比你现在的论文清洗本身更值得收费。**

## 八、第五个问题：Scopus 目前是“文档支持，代码未支持”

README 和 PIPELINE_SPEC 都把 Scopus 写进支持的数据源。

控制台甚至会统计：

> `scopus.csv`

文件数量。

但是业务主流程只有：

```text
IngestWosData
IngestEiData
IngestCnkiData
```

没有 `IngestScopusData`。

所以现在实际状态应该描述为：

> WOS：支持  
> EI：支持  
> CNKI：支持  
> Scopus：规划中

而不是已经支持。

这类“文档跑在实现前面”的问题，在真正收费以后很容易产生信任损耗。

## 九、还有几个技术上我建议尽快修的地方

### DOI 归一化不够

目前主要只是：

> Lowercase + Trim。

最好统一处理：

`https://doi.org/10.xxx`

`doi:10.xxx`

`10.xxx`

否则同 DOI 仍可能不合并。

---

### 标题归一化过于激进

你的算法只留下：

> a-z + 0-9 + 汉字。

那么比如：

> α-phase

和：

> β-phase

希腊字母都可能直接消失。

理论上可能造成两个不同标题归一化成同一个 key。

所以标题不能简单承担“哈希主键”职责。

应该是：

> title similarity + year + authors + journal

综合判断。

---

### Journal Title Case 不建议自己强行改

例如：

> eLife  
> iScience  
> npj Computational Materials

这类期刊的品牌大小写未必符合普通 Title Case。

而你目前使用固定词典保护 IEEE、ASME、AFM 等缩写。

内部 Excel 美化没问题。

作为正式科研数据：

> **优先保存 canonical journal name，不要自行“美化”。**

---

### `On Error Resume Next` 用得太重

尤其整个业务流程里：

```vb
On Error Resume Next
Application.Run ...
Application.Run ...
...
“全流程完成”
```



这意味着某一步异常以后，有可能继续执行，然后给用户一个：

> “成功完成”。

产品阶段应该完全相反：

> **fail loudly + 清晰错误定位 + 哪些步骤成功、哪些失败。**

科研统计产品里：

> 错得明显

往往比：

> 静默地错

安全得多。

## 十、还有一个有趣的判断：VBA 既是你的优势，也是你的劣势

这点我看完代码以后比之前更明确。

### 作为 MVP：VBA 是优势

因为你的用户就在 Excel。

甚至不需要教育用户：

> “请注册账号、上传数据、学习一个新的系统。”

只需要：

> 下载  
> 把 WOS/EI/CNKI 文件扔进目录  
> 打开 Excel  
> 点一下。

这是非常好的早期形态。

---

### 作为正式商业产品：当前“热更新 VBA”是劣势

`Mod_Sync` 需要访问：

> `wb.VBProject`

因此用户还得开启：

> **“信任对 VBA 工程对象模型的访问”**。

再叠加宏安全警告、受信任位置等问题。

对于 10 个熟悉 Excel 的科研秘书，没问题。

对于 1000 个普通 PI：

> 售后噩梦。

所以我不会现在让你重写。

我的建议是：

> **VBA 验证需求 → 找到付费用户 → 再决定迁移。**

而不是：

> 先花几个月重构成漂亮 Web SaaS。

## 十二、为什么我下调了一点商业预期？

因为成果盘点的问题有一个天然缺陷：

> **低频。**

很多课题组真正大规模整理成果的时刻是：

- 年终；
- 职称/考核；
- 学科评估；
- 项目中期；
- 项目结题；
- 申报材料；
- 学院汇总。

它不像文献管理、实验记录、项目管理一样每天用。

所以如果产品只有：

> “导入三份文件 → 给我一个论文 Excel”

用户可能非常喜欢，

但未必愿意：

> ¥499/年持续订阅。

更可能愿意：

> ¥49 / ¥99 / ¥199 买一次工具。

这会限制 SaaS 商业模型。

## 十三、但是这里有一个我认为相当值得发展的方向

不要把产品定义为：

> ### 科研成果管理系统

太大，也已经有人做。

当前就有科研星这样的课题组数字化平台，以及数塔这样的科研成果平台；机构级还有 Elsevier Pure 一类成熟 CRIS，Pure 已经覆盖 publications、people、projects、funding 等完整研究信息管理。

你的产品反而可以非常锐利：

> ### **科研成果“一键盘账”工具**

输入：

**WOS + EI + CNKI + Scopus**

加：

**本组人员名单**

输出的不再只是 7 列：

> 2026 年课题组科研成果报告

自动得到：

- 全部论文；
- SCI/EI/中文重合；
- 第一作者/通讯作者；
- 每位成员成果；
- 年度趋势；
- JCR 分区；
- 中科院分区；
- IF；
- 高被引；
- OA；
- DOI；
- 项目挂靠；
- 各类统计表；
- Word/Excel/PPT 汇报；
- 按学校指定模板导出。

然后让用户直接问：

> “给我生成今年年终总结的成果部分。”

这就开始比现在值钱很多。

## 十四、我现在最建议你做的不是加 AI

而是先做一个东西：

> ### **“异常与待确认中心”**

例如执行结束后不要只告诉用户：

> 成功 545 篇。

而应该出现：

**545 篇确定成果**

**17 篇疑似成果，需要确认**

> Wang J. → 王军 / 王静？

**6 组疑似重复**

> DOI 不同，但标题 98% 相似。

**3 篇来源分类不确定**

> 是否中文核心？

**8 篇日期异常**

> 无法确认正式出版年份。

这会发生一个非常重要的产品变化：

现在的逻辑是：

> **“我替你决定。”**

未来应该是：

> **“机器把 95% 做掉，人只审核最困难的 5%。”**

我认为这才是这个项目真正可能形成竞争力的核心交互。

## 最终判断

读完代码以后，我会把这个项目定义为：

> **一个已经跑出真实业务闭环、值得继续验证的科研行政自动化原型。**

不是玩具。

但也**绝对还没有形成护城河**。

现在最值得保护的不是 VBA 控制台，不是漂亮的 7 列 Excel，也不是“科研台账”这个概念，而是以后逐渐沉淀出来的：

> **多源学术数据统一 → 作者实体识别 → 成果实体消歧 → 评价规则分类 → 用户人工校正反馈**

这条数据处理链。

如果这一条做深，**我会继续做这个项目**。

如果接下来只是继续添加：

> 影响因子列、柱状图、漂亮按钮、更多 Excel 格式……

我反而会建议尽早停，因为很容易变成一个“很好用但很难形成生意”的高级 VBA 工具。

**而且有一件事我建议你现在马上改：把 `Mod0_ControlPanel.bas` 里推算/硬编码的排除数据彻底移除，改为让 `Mod2` 输出真实统计。这个问题的优先级高于任何新功能。** 

如果你愿意，我下一步最有价值的不是继续泛泛讨论，而是可以直接基于这份代码给你做一版 **“产品化路线审计”**：把当前所有功能逐项分成 **保留 / 重构 / 删除 / 下一版新增**，最后收敛成一个我认为最有可能收钱的 v1.0。
