# Release Guide

本文件定义所有项目共用的发布门禁。产品名称、版本来源、构建命令、产物格式、分发渠道和兼容范围由 `PROJECT.md`、包清单及仓库脚本维护。

## 1. 准备发布

1. 确认目标版本已经完成实现、自身验证和开发者验收。
2. 审查 `docs/dev/`：保留仍在进行、待验收或下一版本继续使用的文档；删除前获得明确授权，并确保最终版本已进入 Git 历史。
3. 同步所有受版本约束的清单、锁文件和更新元数据。
4. 将 `CHANGELOG.md` 的 `Unreleased` 更新为目标版本和日期，只记录用户可感知变化与必要迁移说明。
5. 核对 README、许可证、兼容范围、安装方式、隐私说明和支持入口是否与实现一致。

## 2. 验证

使用 `PROJECT.md` 和仓库脚本中记录的唯一检查、测试、构建和打包命令。至少确认：

- 静态检查、自动测试、生产构建和打包全部成功。
- 在声明的主平台和最低兼容版本完成核心冒烟测试。
- 发布包不含测试、开发文档、旧产物、凭证、私有材料、本地路径或无关依赖。
- 记录最终产物的文件名、版本、大小和 SHA-256；后续发布全过程使用同一个已验证文件。
- 明确未覆盖环境、已知限制和回滚方式。

## 3. 最终确认

准备和验证完成后必须停止，向开发者报告：

- 目标版本和准确变更范围；
- 全部验证结果与未覆盖环境；
- 产物路径、大小和 SHA-256；
- 已知限制、兼容性风险和回滚方式。

只有开发者明确确认当前内容是最终发布内容后，才能执行其逐项授权的提交、推送、标签、Release 或发布操作。

- “准备发布”不等于允许对外发布。
- 本地提交也需要单独授权。
- 每个外部渠道都是独立动作，不能相互推定授权。
- 不创建长期 token、自动发布身份或发布工作流，除非开发者先审阅其必要性和维护成本。

## 4. 发布后核验

- 从公开渠道重新获取产物，确认 SHA-256 与已验证文件一致。
- 在干净环境安装并执行核心冒烟测试。
- 核对公开页面的版本、README、许可证、兼容范围和安装说明。
- 记录发布结果；发现阻断问题时停止推广，并按已审阅方案修复或撤回。
